A gateway that reports saving you 73% while billing you 51% more

Paritok compresses AI agent context and reports the savings. On a single measured turn through a real proxy, the reported figure and the actual bill move in opposite directions. This page shows the measurement, the mechanism, and a fix — pin-on-expand — that recovers most of the loss.

The mechanism

The gateway bills for traffic it doesn’t count

When the model calls expand_context, the proxy resolves it inside its own loop, appends the full original to a proxy-local thread, and POSTs that thread upstream again. But stats is computed once in process_request — before that loop runs. The second POST is billed by the provider and never reaches the accounting.

There is a second effect. _conceal_virtual_calls strips the exchange from the reply, so the client agent never sees it. Next turn the agent re-sends the original, Paritok re-compresses it to the same reference, and the model expands it again — every turn, forever.

Paritok’s README does state that /stats is “scoped to what Paritok actually intervenes in.” So this is not a hidden number. The problem is narrower and worse: the excluded traffic is generated by the gateway itself.

The fix

Treat an expansion as an admission

When the model calls expand_context, it is stating that compressing that content was wrong. That is a free supervision signal, and nothing currently uses it. Pin the content and pass it through verbatim from then on — the reference never reappears, so there is nothing left to expand, and the turn costs one POST instead of two.

Pins are keyed by content hash and by source path, so a re-read at a different offset still hits. Content nobody expands is compressed exactly as before.

In the stress case, pinning cuts 22.6% of billed tokens and removes two upstream round-trips. It also drags /stats closer to honest — 45,472 reported against 70,281 billed, versus 16,200 against 90,747 — because pinned passthrough is counted at full size rather than silently excluded.

It does not make Scenario B profitable, and this page will not claim it does. The pin is learned from the first expansion, so the first turn is always paid in full. A session where the model needs exact source every single turn is one where compression cannot win; the honest goal there is to stop losing badly.

Limitations

What would change these numbers

  • The compressor is mocked, not the 4B model. The rig’s measured compression ratio is 0.269 against Paritok’s published 0.257, so magnitudes are representative — but the real model’s output differs.
  • The provider is mocked and the decision to expand is scripted. Real-world expansion rates are unmeasured. Scenario B is a deliberate stress case, not a claim about typical usage; Scenario A is the other extreme.
  • Prompt caching is not modelled. The second POST’s prefix overlaps the first, so real billing is lower than the raw totals here. The expanded original is new input and cannot be a cache hit, so the direction stands — but the magnitude in Scenario B is an upper bound. This is the most important open item.
  • Token counts come from tiktoken over the message payload, excluding system prompt and tool-schema overhead.

Reproduce it

Every number here comes from a script

python harness/mock_upstream.py &
paritok proxy --port 8080 --anthropic-url http://127.0.0.1:9100 --config-file paritok.yaml &
python run_pinned_proxy.py --port 8081 --anthropic-url http://127.0.0.1:9100 --config-file paritok.yaml &

python validate_real_proxy.py   # the finding
python bench_ab.py               # the A/B
python -m pytest tests/ -q   # 5 tests

Restart the proxies between runs — the compression cache and the pin set both persist for the life of the process, and /stats is cumulative.
