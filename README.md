# Pin-on-Expand — teaching Paritok when *not* to compress

Built with [Paritok](https://github.com/Paritok-official/paritok-4b-v1) for the
Token-Efficiency Hackathon.

Paritok compresses agent context and reports the savings. This project shows a
case where the reported savings and the actual bill move in **opposite
directions**, and ships a fix.

**Live demo: https://pin-on-expand.onrender.com** — paste a file, watch it
cold-start two real proxies and reconcile the bill.

Every claim below is produced by a real `paritok proxy` process compressing
through **Paritok's hosted 4B GPU**.

---

Measured against **`paritok` 1.2.8** (PyPI). Every line reference below was
verified to land on the cited code in that released version, and the Docker image
— which installs from PyPI rather than a checkout — reproduces every number.

**Two compressor backends appear in this README.** The headline figures use
Paritok's hosted GPU, i.e. the real 4B model. A deterministic stand-in is also
included so the whole thing reproduces offline with no API key; those numbers are
labelled *(mock)* and are close but not identical, because the two compressors
compress differently. Nothing else about the measurement changes between them —
the proxies, the resolve loop and the token accounting are real either way.

## The finding

When the model calls `expand_context`, the proxy resolves it in its own loop
(`proxy/server.py:696-748`), appends the full original to a proxy-local thread,
and POSTs that thread upstream again (`server.py:705-706`).

Two consequences:

1. **Those tokens are billed but not counted.** `stats` is computed once in
   `process_request`, *before* the resolve loop runs. The second POST never
   reaches the accounting.
2. **The expansion does not persist.** `_conceal_virtual_calls` (`server.py:678`)
   strips the exchange from the reply, so the client agent never sees it. Next
   turn the agent re-sends the original, Paritok re-compresses it to the same
   `[REF:id]`, and the model expands it again.

Paritok's README is explicit that `/stats` is "scoped to what Paritok actually
intervenes in", so this is not a hidden number. The problem is narrower and
worse: the excluded traffic is *generated by the gateway itself*.

### Measured, one client turn, hosted GPU

Fixture: `/usr/lib/python3.12/argparse.py`, 20,005 tokens.

```
post 0:  6,919 tokens   compressed request
post 1: 26,924 tokens   carries the full expanded original
                        ─────────
billed:                 33,843
```

`/stats` for that same turn:

```
input_tokens_original    : 20,036      compression_ratio : 0.360
input_tokens_compressed  :  7,204      tokens billed but uncounted : 26,639
```

**Reported: 64.0% saved. Actual: 69.2% more than sending the file uncompressed.**

The same run against the offline stand-in *(mock)*: 5,113 + 25,118 = 30,231
billed, 73.1% reported, 50.9% overspend. Different compressor, same shape.

Reproduce offline: `python validate_real_proxy.py`

## The fix

Treat `expand_context` as supervision. When the model expands a ref, it has
stated that compressing that content was wrong. Pin it and pass it through
verbatim from then on — the `[REF:id]` never reappears, so there is nothing left
to expand and the turn costs one POST instead of two.

Pins are keyed by content hash and by source path, so a re-read at a different
offset still hits. Content nobody expands is compressed exactly as before.

```python
from paritok_adaptive import install
install()   # rebinds ParitokEngine before proxy/server.py constructs it
```

No fork required — `server.py` imports `ParitokEngine` inside `run_proxy`
(`server.py:275`), so rebinding the name is enough.

### A/B, 3 turns, hosted GPU, both real proxy processes

No proxy at all would bill **60,015**.

| Scenario A — model never expands *(control)* | POSTs | Billed | Reported | vs no proxy |
|---|--:|--:|--:|--:|
| stock Paritok | 3 | 20,787 | 21,612 | **+65.4%** |
| pin-on-expand | 3 | 20,787 | 21,612 | **+65.4%** |

| Scenario B — model expands each turn | POSTs | Billed | Reported | vs no proxy |
|---|--:|--:|--:|--:|
| stock Paritok | 6 | 104,229 | 22,932 | **−73.7%** |
| pin-on-expand | 4 | 73,901 | 47,276 | **−23.1%** |

→ **29.1% fewer billed tokens, 2 fewer upstream round-trips.**

The same A/B against the offline stand-in *(mock)*: control 15,366 both,
+74.4%; stress 90,747 → 70,281, −51.2% → −17.1%, 22.6% saved. **The fix performs
better against the real model than against the stand-in**, not worse.

Reproduce offline: `python bench_ab.py` · Live: the app above.

Two things worth reading carefully:

- **The control is a dead heat.** Pinning changes nothing for sessions that
  never expand. It narrows compression only where the model has demonstrated
  compression was wrong.
- **Pinning does not make Scenario B profitable, and this README will not claim
  it does.** It recovers most of the loss (−73.7% → −23.1%). It cannot recover
  the first turn, because the pin is *learned* from the first expansion. A
  session where the model needs exact source every single turn is one where
  compression cannot win; the honest goal is to stop losing badly.

`/stats` also gets closer to the truth under pinning (47,276 reported against
73,901 billed, versus 22,932 against 104,229) because pinned passthrough is
counted at full size rather than silently excluded.

## The app

**https://pin-on-expand.onrender.com**

A web UI that runs the whole thing live: paste a source file, and it cold-starts
**two real `paritok proxy` processes** — one stock, one with `install()` applied —
drives a real multi-turn session through each over HTTP, and reconciles what was
billed against what was reported.

```bash
pip install -r requirements.txt
PORT=8420 uvicorn app.main:app --port 8420
```

Set `PARITOK_API_KEY` to compress through Paritok's hosted 4B GPU instead of the
in-process mock compressor; the app shows which backend is live in the header.

A run takes roughly **20s on the stand-in and ~110s on the hosted GPU**, because
every segment makes a round trip to Paritok. Runs are asynchronous — the endpoint
returns a job id and the UI polls it, so the progress it shows is the server's
actual state rather than a timer.

The provider is always mocked. That is not a shortcut — a real provider will
neither let us script when the model calls `expand_context` nor report exactly
what each POST was billed, and both are the measurement.

Deploy with the included `Dockerfile` / `render.yaml`.

### Why it cold-starts the proxies on every run

The compression cache, the shadow store and the pin set all live for the life of
the proxy process, and `/stats` is cumulative. A warm proxy silently returns a
previous run's result. Restarting is the only way a run means what it says.

## Limitations

Stated plainly, because several of these would change the numbers:

- **The compressor is real** for every headline number — Paritok's hosted 4B GPU.
  The offline stand-in exists only so the repo reproduces without an API key, and
  its figures are labelled *(mock)* wherever they appear.
- **The measured compression ratio was 0.360**, against Paritok's published
  0.257, on stdlib Python — in-domain code, not an adversarial fixture. Worth
  noting rather than explaining away; it is one file, and one file is not a
  benchmark.
- **The provider is mocked**, and the model's decision to expand is scripted.
  Real-world expansion rates are unmeasured. Scenario B (expand every turn) is a
  deliberate stress case, not a claim about typical usage; Scenario A is the
  other extreme.
- **Prompt caching is not modelled.** The second POST's prefix overlaps the
  first, so real billing is lower than the raw totals here. The expanded
  original is new input and cannot be a cache hit, so the direction stands, but
  the magnitude in Scenario B is an upper bound. This is the most important open
  item.
- **One fixture, one session shape.** Every figure here comes from `argparse.py`
  driven through three turns. The direction is robust across backends; the
  magnitudes are a single data point, not a distribution.
- Token counts come from `tiktoken` over the message payload, excluding system
  prompt and tool-schema overhead.

## Reproducing

```bash
python -m venv .venv && ./.venv/bin/pip install -e /path/to/paritok-4b-v1 --no-deps
./.venv/bin/pip install tiktoken pyyaml httpx click pytest uvicorn starlette

python harness/mock_upstream.py &
paritok proxy --port 8080 --anthropic-url http://127.0.0.1:9100 --config-file paritok.yaml &
python run_pinned_proxy.py --port 8081 --anthropic-url http://127.0.0.1:9100 --config-file paritok.yaml &

python validate_real_proxy.py    # the finding
python bench_ab.py               # the A/B
python -m pytest tests/ -q       # 5 tests
```

**Restart the proxies between measurement runs.** The in-process compression
cache and the pin set both persist for the life of the process, and `/stats` is
cumulative.

## Notes for the Paritok team

Filed as feedback rather than asserted as bugs:

1. `/stats` excludes resolve-loop traffic that the proxy itself generates.
   Counting the extra POSTs would make the dashboard reflect the bill.
2. `served_refs` (`server.py:728`) dedupes expansions within a turn but not
   across turns, and `_conceal_virtual_calls` guarantees nothing carries over.
3. The `level` parameter (L0–L3) is fully implemented but nothing selects
   between values: tool results always take the `DEFAULT_LEVEL` of L1, history
   is hardcoded to L3. The adaptive-compression roadmap item is mostly a policy
   question, not a modelling one — the dial already exists.
