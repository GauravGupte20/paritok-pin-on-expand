## Issue 1

### Title

`/stats` excludes the resolve-loop traffic the proxy itself generates

### Body

Measured against `paritok` 1.2.8 (PyPI), compressing on the hosted GPU.

`stats` is computed once in `process_request`, before `_anthropic_resolve` runs
its virtual-tool loop. When the model calls `expand_context`, that loop appends
the full original to a proxy-local `thread` and POSTs it upstream again
(`proxy/server.py:705-706`). Those tokens are billed by the provider and never
reach the accounting.

One client turn, `argparse.py` (20,005 tokens) as a `tool_result`, hosted GPU:

```
post 0:  6,919 tokens   compressed request         <- counted by /stats
post 1: 26,924 tokens   carries the full original  <- not counted
                        ---------
billed:  33,843
```

`/stats` for that turn:

```
input_tokens_original   : 20,036
input_tokens_compressed :  7,204
```

So `/stats` reports a **64.0% saving** on a turn that billed **69.2% more** than
sending the file uncompressed. 26,639 tokens were billed and uncounted.

I understand the README's position that `/stats` is "scoped to what Paritok
actually intervenes in", and I don't think the number is dishonest. The issue is
narrower: this particular excluded traffic is *generated by the gateway itself*,
which makes it the one category a user would most expect to see counted. A user
reading `estimated_cost_saved_usd` has no way to discover it.

**Suggested fix:** accumulate token counts for each POST inside
`_anthropic_resolve` / `_openai_resolve` and add them to the request's stats
before returning, or expose them as a separate `resolve_loop_tokens` field so the
two are distinguishable.

**Reproducer:** https://github.com/GauravGupte20/paritok-pin-on-expand —
`python validate_real_proxy.py` runs it against a real proxy with a mock provider
that records every upstream POST.

## Issue 2

### Title

`expand_context` results never reach the client, so the model re-expands the same ref every turn

### Body

Measured against `paritok` 1.2.8.

`served_refs` (`proxy/server.py:728`) dedupes expansions within a single turn's
resolve loop. But `_conceal_virtual_calls` (`server.py:678`) strips the virtual
exchange from the reply, so the client agent never sees it and it never enters
the client's conversation history.

The consequence is that the expansion is discarded at the end of every turn. Next
turn the agent re-sends the original file, Paritok re-compresses it to the same
`[REF:id]` (the cache hits, since `sid` is a content hash), and the model calls
`expand_context` on it again. There is no cross-turn memory of the fact that this
content was already needed in full.

Over a 3-turn session where the model needs exact source each turn:

```
6 upstream POSTs for 3 client turns
104,229 tokens billed, against 60,015 for no proxy at all
```

**Suggested fix:** persist expanded shadow ids for the conversation (the
`session_id` from `_conversation_id` is already computed) and skip compressing
content whose ref has been expanded before. I implemented exactly this as a
subclass of `CompressionPipeline` / `ParitokEngine` — no fork needed, since
`server.py:275` imports `ParitokEngine` inside `run_proxy`, so rebinding the name
is enough.

Measured effect on the same session: 4 POSTs instead of 6, **29.1% fewer billed
tokens**. When the model never expands, behaviour is byte-identical to stock — it
only narrows compression where the model has demonstrated compression was wrong.

**Implementation:** `paritok_adaptive/pin.py` in
https://github.com/GauravGupte20/paritok-pin-on-expand — happy to open a PR
against this repo if the approach looks right to you.

## Issue 3

### Title

The L0–L3 `level` dial is implemented but nothing ever selects between values

### Body

The roadmap lists adaptive compression — "per-segment auto-selection of
compression aggressiveness based on age, kind, and downstream intent" — as
upcoming work. Reading 1.2.8, most of the mechanism already ships; what's missing
is only the policy.

`CompressionPipeline.compress()` (`pipelines/compress.py:127`) takes `level`,
`kind` and `source`. `LocalModelStrategy` maps L0–L3 to real target ratios
(≤0.50 / ≤0.35 / ≤0.25 / ≤0.20). But at the two call sites:

- tool-result compression (`middleware/wrapper.py:418`) never passes `level`, so
  everything falls through to `DEFAULT_LEVEL` = L1
- history compression (`wrapper.py:543`) hardcodes `level="L3"`

So every tool result in every session is compressed at exactly one aggressiveness,
regardless of age, kind, or relevance to the current task.

This seems worth flagging because it makes the roadmap item much smaller than it
looks: the dial exists and is wired through to the model, and `bge-small` is
already a dependency for tool discovery, so intent-similarity scoring needs no new
package. What's missing is a function choosing a level per segment.

Not filing this as a bug — it's a note that the remaining work may be a policy
question rather than a modelling one.
